1부

토대

라이브러리와 무관하게 성립하는 것들. Java를 떠나도 따라오는 지식이다.

1.1테스트는 무엇을 사는가

"테스트를 짜면 버그가 줄어든다"는 설명은 절반만 맞다. 테스트가 실제로 사는 것은 세 가지이고, 그중 버그 검출은 가장 값싼 축에 속한다.

① 회귀 안전망 — 바꿀 자유

코드를 고치는 일이 두려운 이유는 무엇이 깨졌는지 알 방법이 없기 때문이다. 테스트가 있으면 "고치고 → 돌리고 → 초록" 이 3초 만에 끝난다. 없으면 손으로 화면을 클릭하거나, 아예 안 고치고 만다. 테스트가 진짜로 파는 상품은 리팩터링할 용기다.

② 설계 압력 — 짜기 어려우면 설계가 나쁘다

이건 부수 효과가 아니라 핵심이다. 테스트하기 어려운 코드에는 거의 항상 이유가 있다.

테스트가 어렵다설계가 말하는 것
객체를 만들려면 DB가 떠야 한다도메인 규칙이 인프라와 붙어 있다
new를 메서드 안에서 한다의존을 바꿔 끼울 수 없다
검증하려면 private을 열어야 한다책임이 잘못된 클래스에 있다
세팅 코드가 30줄이다이 클래스가 아는 것이 너무 많다

이 저장소의 ch03_mockito/OrderService가 생성자 주입을 쓰는 것도 그래서다. 필드 주입이면 @InjectMocks가 조용히 null을 남길 수 있다 — 테스트하기 쉬운 설계가 대개 좋은 설계인 사례를 코드로 박아 둔 것이다.

③ 실행되는 명세

주석은 썩는다. 코드와 어긋나도 아무도 모른다. 테스트는 어긋나는 순간 빨간불이 되므로, 절대 낡지 않는 유일한 문서다. 그래서 이 저장소의 테스트 이름이 결제_실패시_FAILED로_저장한다처럼 문장으로 되어 있다.

정의

회귀(regression) — 예전에 되던 것이 변경 때문에 안 되게 되는 것. 새 기능의 버그보다 훨씬 비싸다. 아무도 그 자리를 다시 보지 않기 때문이다.

1.2피라미드, 그리고 그 반론

Mike Cohn이 2009년에 제시한 그림이다. 아래로 갈수록 싸고 빠르고 많이, 위로 갈수록 비싸고 느리고 적게.

왜 이 모양이어야 하나. 피드백 루프의 길이 때문이다. 단위 테스트 500개가 2초에 끝나면 저장할 때마다 돌릴 수 있다. E2E 500개가 40분 걸리면 하루에 한 번 돌린다 — 그때쯤 원인이 될 만한 커밋이 스무 개다.

아이스크림 콘

피라미드가 뒤집힌 모양을 아이스크림 콘 안티패턴이라 부른다. E2E가 잔뜩, 단위는 거의 없는 상태. 증상은 이렇다 — CI가 20분씩 걸리고, 실패했을 때 원인이 어디인지 아무도 모르고, "그거 재실행하면 통과해요"라는 말이 팀에서 정상 대화가 된다.

반론: Testing Trophy

Kent C. Dodds가 제기한 반론은 이렇다. 단위 테스트가 많으면 각각은 통과하는데 합쳐 놓으면 안 되는 상황이 생긴다. 목을 잔뜩 끼운 단위 테스트는 "내 가정 안에서는 맞다"만 증명하기 때문이다. 그래서 통합 테스트가 가장 두꺼워야 한다는 주장이다.

어느 쪽이 옳은가? 실무의 답은 대상에 따라 다르다이다. 도메인 규칙이 복잡하면 단위가 값어치 있고, 대부분이 배선과 입출력이면 통합이 값어치 있다. 웹 API 서버는 대체로 후자에 가깝다 — 그래서 이 저장소도 4장에서 슬라이스 통합 테스트에 가장 큰 비중을 둔다.

Spring에서의 대응

단위 = 프레임워크 없이 new로 만들어 테스트 (1~3장) · 슬라이스 = 한 계층만 세우는 통합 (@WebMvcTest, @JsonTest — 4~5장) · 통합 = 전체 컨텍스트 (@SpringBootTest) · E2E = 실제 서버 + 실제 DB (RANDOM_PORT + Testcontainers)

1.3테스트 더블 다섯 종

Gerard Meszaros가 분류한 다섯이다. 흔히 전부 "목"이라 부르지만, 구별하면 설계 대화가 정확해진다. 스턴트 더블(대역 배우)에서 온 이름이다 — 진짜 배우 대신 위험한 장면을 찍는다.

종류하는 일예
Dummy 자리만 채운다. 실제로 쓰이지 않는다 생성자가 요구해서 넘기는 null이나 빈 객체
Fake 진짜로 동작하는 가벼운 구현 인메모리 Map 저장소, H2 인메모리 DB
Stub 정해진 값을 돌려준다. 상태 검증용 when(repo.findById(1L)).thenReturn(...)
Spy 진짜를 감싸 호출을 기록한다 Mockito.spy(new ArrayList<>())
Mock 기대한 대로 불렸는지 행위를 검증 verify(gateway, times(1)).charge(...)
핵심 구분

Stub은 상태를, Mock은 행위를 검증한다.
"결과가 PAID인가"는 상태 검증이다 → Stub이면 충분하다.
"결제사를 정확히 한 번 불렀는가"는 행위 검증이다 → Mock이 필요하다.

Mockito는 이 둘을 한 객체로 제공한다. when(...)을 쓰면 Stub으로, verify(...)를 쓰면 Mock으로 쓰는 것이다.

왜 이 구분이 중요한가 — 중복 청구 예제

ch03_mockito/OrderService의 결제 흐름을 보자. 구현에 실수로 charge()가 두 번 불리는 버그가 들어갔다고 하자.

assertThat(result.status()).isEqualTo(PAID)는 통과한다. 이 버그를 잡는 것은 오직 한 줄이다: 

verify(paymentGateway, times(1)).charge("CUST-5", BigDecimal.valueOf(7000));
함정

반대 방향의 남용이 더 흔하다. 값 계산만 하면 되는 곳에 목을 끼우면, 테스트가 "구현이 이 순서로 이걸 부른다"에 묶인다. 리팩터링할 때마다 깨지는데 동작은 멀쩡하다 — 이런 테스트는 안전망이 아니라 족쇄다.

판단 기준: 검증하려는 것이 반환값이면 목을 쓰지 말 것.

1.4FIRST — 좋은 테스트의 조건

Robert C. Martin이 정리한 다섯 글자. 각각이 어긋났을 때의 증상까지 알아 두면 쓸모가 있다.

뜻어겼을 때의 증상
Fast빠르다안 돌리게 된다. 안 돌리는 테스트는 없는 것과 같다
Independent서로 독립적"혼자 돌리면 통과, 전체로 돌리면 실패"
Repeatable어디서든 같은 결과내 노트북에선 되는데 CI에선 깨짐
Self-validating초록/빨강으로 스스로 판정로그를 눈으로 읽어야 함 → 아무도 안 읽음
Timely제때(가능하면 코드보다 먼저) 쓴다나중에 쓰면 "테스트 가능한 형태"가 아니게 되어 있다

Independent가 공짜로 오는 이유

JUnit 5의 기본 생명주기는 PER_METHOD다 — 테스트 메서드마다 인스턴스를 새로 만든다. 그래서 필드에 남긴 상태가 다음 테스트로 넘어가지 않는다.

주의

@TestInstance(PER_CLASS)를 걸면 인스턴스를 하나만 만든다. @BeforeAll이 static이 아니어도 되어 편하지만, 테스트 간 상태가 공유된다 — Independent를 스스로 포기하는 것이다. 얻는 편의보다 잃는 격리가 클 때가 많다.

1.5AAA와 Given-When-Then

같은 구조에 붙은 두 이름이다. 테스트를 세 덩어리로 나눈다.

AAABDD하는 일
ArrangeGiven전제를 세운다 (객체 생성, 스터빙)
ActWhen검증 대상 동작을 딱 한 번 실행한다
AssertThen결과를 확인한다

이 구조가 강제하는 규율이 하나 있다. Act가 한 줄이어야 한다는 것. Act가 여러 줄이면 그 테스트는 두 가지를 검증하고 있고, 실패했을 때 어느 쪽인지 모른다. 

// ch03_mockito/MockitoBasicsTest — BDDMockito 스타일
// given
Order pending = Order.pending("ORD-8", "CUST-8", 12_000);
given(orderRepository.findById("ORD-8")).willReturn(Optional.of(pending));
given(paymentGateway.charge(anyString(), any())).willReturn("APPROVED-8");

// when
Order result = orderService.pay("ORD-8");          ← 딱 한 줄

// then
assertThat(result.status()).isEqualTo(Status.PAID);
then(paymentGateway).should().charge("CUST-8", BigDecimal.valueOf(12_000));
BDDMockito가 존재하는 이유

Mockito의 when()은 "스터빙"과 "실행 단계" 두 뜻으로 읽혀 헷갈린다. given()/willReturn()은 기능이 같고 이름만 다르다 — given 블록에서는 given을, then 블록에서는 then을 쓰면 구조와 어휘가 일치한다.

1.6TDD 사이클

Kent Beck의 Red-Green-Refactor. 세 단계 각각에 지켜야 할 규칙이 있다.

가장 흔한 실수

Red 단계를 건너뛰는 것. 테스트를 짜고 곧바로 구현한 뒤 초록을 보면, 그 테스트가 정말로 무언가를 검증하는지 확인한 적이 없다.

실제로 이런 일이 생긴다 — 단언을 빠뜨렸거나, SoftAssertions에서 assertAll()을 안 불렀거나, assumeTrue가 항상 거짓이라 늘 건너뛰거나. 세 경우 모두 테스트는 영원히 초록이고, 아무것도 지키지 않는다.

이 저장소의 연습문제가 실패 상태로 시작하는 것이 바로 Red다. ./gradlew exercise를 처음 돌리면 26개가 빨간불이고, 그것을 초록으로 만드는 것이 학습 루프다.

1.7테스트 가능한 설계

1.1에서 "테스트가 어려우면 설계가 나쁘다"고 했다. 그 반대 방향, 즉 무엇을 하면 테스트 가능해지는가를 보자.

핵심은 의존성 주입 하나다

인터페이스로 두는 이유

ch03_mockito/PaymentGateway가 인터페이스인 것은 우연이 아니다. 서비스의 규칙을 검증할 때 그 구현이 HTTP인지 DB인지 알 필요가 없다. 이 경계를 포트(port)라 부르고, 실제 구현을 어댑터(adapter)라 부른다.

험블 객체 패턴

테스트하기 어려운 것(프레임워크, DB, 네트워크, 시각, 난수)에 붙은 코드를 최대한 얇게 만들고, 로직은 전부 테스트 가능한 순수 객체로 밀어내는 방식이다.

컨트롤러가 얇아야 하는 이유가 이것이다. ch04_springslice/ArticleController는 "받아서 넘기고 상태 코드를 정한다"밖에 하지 않는다.

시각과 난수 — 잊기 쉬운 두 의존

LocalDateTime.now()와 Math.random()은 숨은 의존이다. Repeatable을 깨뜨리고, "자정 근처에서만 깨지는 테스트" 같은 것을 만든다. 해법은 같다 — 밖에서 주입한다. Java는 이를 위해 Clock을 제공한다. 

// ✗ 테스트가 오늘 날짜에 좌우된다
if (order.createdAt().isBefore(LocalDateTime.now().minusDays(7))) { ... }

// ✔ Clock 을 주입하면 "2026-08-17 10:00 인 세계"를 만들 수 있다
if (order.createdAt().isBefore(LocalDateTime.now(clock).minusDays(7))) { ... }

1.8테스트하지 말아야 할 것

테스트를 늘리면 항상 좋다는 생각은 틀렸다. 유지 비용이 있고, 잘못된 테스트는 리팩터링을 막는다. 쓰지 말아야 할 것들:

  • getter/setter, 자동 생성 코드 — 프레임워크와 컴파일러를 테스트하는 것이다
  • private 메서드 — 검증하고 싶다면 그건 다른 클래스로 나와야 한다는 신호다
  • 구현 세부사항 — "내부에서 HashMap을 쓴다" 같은 것. 동작이 같은데 자료구조를 바꿨다고 테스트가 깨지면 안 된다
  • 남의 라이브러리 — Jackson이 JSON을 만드는지가 아니라, 우리 DTO의 계약이 지켜지는지를 본다 (5장의 주제가 정확히 이것이다)
판단 기준 한 줄

"이 동작이 깨지면 사용자가 아플까?" — 아프면 테스트한다. 안 아프면 안 한다.
커버리지 숫자는 이 질문의 답이 아니다. 100%인데 아무것도 못 잡는 스위트를 만들 수 있다.

2부

Spring은 뒤에서 무엇을 하는가

여기부터는 Spring에 한정된다. 어노테이션 하나를 붙였을 때 실제로 벌어지는 일들.

2.1TestContext Framework 전체 그림

@SpringBootTest나 @WebMvcTest를 붙이면 JUnit이 아니라 Spring TestContext Framework가 일을 시작한다. 순서는 이렇다.

핵심

Spring 테스트가 느린 이유는 컨텍스트 기동이지 테스트 자체가 아니다. 그래서 2부의 대부분은 "어떻게 하면 컨텍스트를 덜 띄우나"에 관한 이야기다.

2.2슬라이스는 어떻게 빈을 고르나

@WebMvcTest는 마법이 아니다. 정체는 TypeExcludeFilter다 — 컴포넌트 스캔 도중 "이 타입은 제외" 판정을 내리는 필터. WebMvcTypeExcludeFilter가 웹 계층으로 분류된 것만 통과시킨다.

통과 목록은 정해져 있다. 외울 필요는 없지만 세 가지는 기억할 값어치가 있다.

통과 (세워진다)차단 (안 세워진다)
@Controller, @RestController@Service
@ControllerAdvice@Repository
@JsonComponent, Converter@Component 일반
Filter, HandlerInterceptorJPA · DataSource
WebMvcConfigurer일반 @Configuration
놓치기 쉬운 셋

① @ControllerAdvice는 포함된다. 그래서 목이 예외를 던지면 실제 예외 처리 경로가 그대로 돈다 — 404 응답 본문의 모양까지 검증할 수 있다. ch04_springslice/ArticleControllerWebMvcTest의 없으면_404와_에러본문을_준다가 그것이다.

② Filter도 포함된다. Spring Security를 쓰면 보안 필터가 그대로 걸려 "왜 401이 나오지?"를 겪는다.

③ 컨트롤러를 지정하지 않으면 전부 세운다. @WebMvcTest만 쓰면 프로젝트의 모든 컨트롤러가 올라오고, 그들이 쓰는 서비스를 전부 목으로 채워야 컨텍스트가 뜬다.

2.3컨텍스트 캐싱 — 가장 큰 성능 레버

Spring은 설정이 같으면 컨텍스트를 재사용한다. 테스트 클래스가 100개여도 설정이 3종이면 컨텍스트는 3개만 뜬다. 반대로 설정이 100종이면 100번 뜬다 — 이것이 "테스트가 갑자기 느려졌다"의 거의 유일한 원인이다.

캐시 키는 무엇으로 이루어지나

가장 비싼 실수

@MockitoBean은 캐시 키의 일부다. 테스트 클래스마다 다른 조합으로 목을 끼우면, 클래스마다 새 컨텍스트가 뜬다.

같은 이유로 properties = {"a=1"}을 한 클래스에만 추가하는 것, @ActiveProfiles를 제각각 붙이는 것도 전부 컨텍스트를 늘린다. 설정 조합을 소수로 수렴시키는 것이 테스트 스위트 최적화의 첫 수단이다.

캐시 크기는 기본 32개(spring.test.context.cache.maxSize)이고, 넘치면 LRU로 버린다. 버려진 컨텍스트가 다시 필요하면 또 띄운다.

진단 방법

logging.level.org.springframework.test.context.cache=DEBUG를 켜면 캐시 적중/실패와 현재 크기가 찍힌다. 스위트가 느릴 때 가장 먼저 볼 자리다.

2.4MockMvc는 서버 없이 어떻게 도나

MockMvc는 HTTP를 흉내내는 것이 아니다. 서블릿 API를 가짜로 만들고 DispatcherServlet을 직접 호출한다. 소켓도, 포트도, 톰캣도 없다.

그래서 무엇을 검증할 수 있나

URL 매핑 · 경로 변수 변환 · @Valid 검증 · 메시지 컨버터(JSON 직렬화) · 예외 → 응답 변환 · 인터셉터 · 필터. 웹 계층에서 사고가 나는 자리는 거의 다 여기 있다.

보지 못하는 것

실제 소켓·커넥션·타임아웃, 서블릿 컨테이너 고유 설정, 진짜 인코딩 협상. 이런 것이 필요하면 @SpringBootTest(webEnvironment = RANDOM_PORT) + TestRestTemplate으로 간다 — ch04_springslice/SpringBootTestComparisonTest가 둘을 나란히 보여준다.

⚠ 여기서 나오는 한글 깨짐도 이 구조에서 나온다. getContentAsString()은 ISO-8859-1로 읽으므로 StandardCharsets.UTF_8을 명시해야 한다.

2.5@MockitoBean의 빈 교체

@Mock과 @MockitoBean은 이름이 비슷하지만 작동 층이 다르다.

@Mock (Mockito)@MockitoBean (Spring)
만드는 주체MockitoExtensionSpring TestContext
어디에 넣나테스트 클래스의 필드애플리케이션 컨텍스트의 빈으로 등록
Spring 필요?아니오예
캐시 키 영향없음있음 (2.3 참고)
쓰는 곳순수 단위 테스트 (3장)슬라이스·통합 테스트 (4장)

Spring Framework 6.2에서 도입된 Bean Override 메커니즘이 그 정체다. 컨텍스트를 만들 때 BeanFactoryPostProcessor가 끼어들어 해당 타입의 빈 정의를 목 인스턴스로 갈아치운다. 원래 빈이 없어도 새로 등록해 준다 — @WebMvcTest에서 서비스가 아예 안 세워지는데도 목이 들어가는 것이 그래서다.

버전 주의

@MockBean은 Spring Boot 3.4 / Framework 6.2부터 deprecated다. 새 코드는 @MockitoBean을 쓴다. 패키지도 다르다 — org.springframework.test.context.bean.override.mockito.

인터넷의 예제 대부분이 아직 옛 이름을 쓰고 있으니, 복사해 올 때 확인할 것.

2.6트랜잭션 롤백과 그 구멍

테스트에 @Transactional을 붙이면 Spring이 끝날 때 롤백한다 (@DataJpaTest는 기본으로 이렇게 동작한다). DB를 건드리는 테스트가 서로를 오염시키지 않게 하는 표준 수단이다.

이 편의가 숨기는 세 가지
  • 커밋 시점에만 터지는 문제를 못 본다 — 지연된 제약 조건, flush 타이밍 문제. 실제로 커밋해 봐야 알 수 있는 것들이다.
  • 같은 트랜잭션이라 1차 캐시가 살아 있다. save() 후 findById()가 DB를 안 가고 영속성 컨텍스트에서 나올 수 있다 — "실제로 저장됐는가"를 검증한 것이 아니다. flush()/clear()를 명시하는 이유다.
  • RANDOM_PORT에서는 롤백이 안 먹는다. 진짜 HTTP 요청은 다른 스레드에서 처리되어 테스트의 트랜잭션 밖이다. 이때는 데이터를 직접 지우거나 Testcontainers로 DB 자체를 갈아야 한다.

이 저장소의 4장이 DB 대신 인메모리 Map을 쓰는 것도 이 복잡도를 피하기 위해서다 (ch04_springslice/ArticleService). 웹 계층을 배우는 자리에 JPA를 끌어들이면 배울 것이 흐려진다. 진짜 DB는 Testcontainers와 함께 다뤄야 할 별도 주제다.
